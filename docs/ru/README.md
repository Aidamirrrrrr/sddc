# Документация sddc

sddc составляет спецификацию по исходному запросу и ответам пользователя.
Он работает как проверка качества требований: обнаруживает недостающие решения,
противоречия и слишком крупные задачи, но не придумывает ответы самостоятельно.

## Что вы подтверждаете

- **Требования** описывают ожидаемое изменение и критерии приёмки.
- **Карта проекта** фиксирует существующий связанный код, тесты и ограничения.
- **Технический план** фиксирует подход, изменяемые контракты и модель данных.
- **Граф задач** перечисляет конкретные изменения файлов, волны зависимостей и
  команды проверки.

Это не четыре версии одного документа. Каждый следующий этап добавляет только тот
уровень деталей, который невозможно определить на предыдущем. В терминале они
показываются как обычный текст; YAML хранится только в `.specs` для возобновления
работы и автоматической проверки.

Перед созданием спеки intent-gate отделяет задачи на изменение от read-only
вопросов о репозитории. Неоднозначный запрос возвращается пользователю для
уточнения.

## Вопросы о репозитории

Для запроса на объяснение, исследование или ревью sddc не создаёт спеку.
Он предлагает связанные файлы, позволяет пользователю управлять контекстом,
читает только подтверждённые snapshots и выдаёт проверенный ответ с файловыми
evidence и явными неизвестными. Этот путь не может планировать или выполнять
изменения исходного кода.

## Как работает pipeline

1. Запрос классифицируется как изменение проекта, read-only вопрос или неоднозначное намерение.
2. Для изменения агент предлагает файлы, а пользователь разрешает модели прочитать контекст до спеки.
3. Из запроса извлекаются только явно указанные факты и язык запроса.
4. Единый анализ определяет готовность запроса, необходимость вопросов или
   декомпозиции.
5. Отдельный reviewer проверяет анализ по фактам запроса и подтверждённому коду. Для вопросов и
   декомпозиции pipeline завершается после этого третьего вызова.
6. Для готового запроса формируется спецификация.
7. Спецификация проходит финальную проверку по чек-листу.

Существующие сигнатуры, usages, тесты и module wiring определяются по
подтверждённым snapshots. Пользователю задаются только вопросы о недостающих
продуктовых или необратимых архитектурных решениях.

Выбор и расширение контекста используют два LLM-вызова до спеки. Затем неполная
или крупная спецификация использует три вызова, а готовая — пять. Невалидный
анализ получает один дополнительный repair-вызов.

Если любой этап возвращает пустой или не соответствующий схеме structured
output, клиент отправляет модели исходный контекст и ошибку на одну повторную
попытку. Бесконечных retry нет.

В интерактивном терминале статус `needs_clarification` запускает новый раунд
вопросов. Ответы добавляются к исходному запросу, после чего весь pipeline
выполняется заново. Цикл заканчивается только со статусом `ready` или
`needs_decomposition`. Пустой ответ не принимается; прервать диалог можно через
`Ctrl+C`.

Готовая спецификация показывается компактным итогом и требует явного решения:
принять, открыть полный документ или исправить. При отклонении пользователь описывает,
что именно нужно изменить. Отклонённая YAML-спека и комментарий добавляются в
контекст, после чего pipeline запускается заново. Только принятая версия
сохраняется как `spec.yaml`.

При чтении из pipe агент не может задавать вопросы или получить подтверждение,
поэтому выводит результат и сохраняет его как `spec.draft.yaml`.

## Исследование репозитория

После принятия спеки со статусом `ready` агент превращает уже подтверждённый
контекст в read-only discovery:

1. Индексирует безопасные файлы проекта без чтения содержимого.
2. Модель рекомендует не более 12 релевантных файлов и объясняет каждый выбор.
3. Пользователь ищет, включает или отключает файлы и при необходимости добавляет
   контекст проекта.
4. Агент читает только подтверждённые текстовые файлы в пределах лимита размера.
5. Модель может запросить до шести дополнительных файлов. Второе подтверждение
   появляется только если набор действительно изменился.
6. После принятия спеки модель описывает стек, структуру, связанные файлы, соглашения, тесты,
   ограничения и неизвестные факты.
7. Второй вызов удаляет выводы без файловых evidence.
8. Краткое понимание проекта показывается пользователю и исправляется до явного принятия;
   полный discovery открывается по отдельному действию.

`.env`, приватные ключи, `.git`, `.specs`, зависимости и build output никогда не
передаются модели. Discovery ничего не проектирует и не изменяет. Результат
сохраняется как `.specs/<feature>/discovery.yaml`.

Селектор показывает причину рекомендации, поддерживает поиск по мере ввода и не
позволяет выбрать больше 24 файлов или 200 KiB. Дополнительный контекст считается
утверждением пользователя, но не файловым evidence.
Подтверждённые пути и пользовательский контекст записываются в `discovery.yaml`.
Рабочая область помечает рекомендованные, тестовые, конфигурационные и остальные
файлы, позволяет просматривать выбранные файлы, показывает оценку токенов и
стоимости и хранит переиспользуемые профили в `.specs/context-profiles/`.

Для принятой декомпозиции discovery не запускается: сначала должна быть выбрана
и описана конкретная подзадача.

## Планирование реализации

После принятия discovery планирование решает только одно: *как* делается
изменение. Этапы:

1. Черновик технического подхода, изменяемых контрактов и модели данных на
   основе `spec.yaml` и `discovery.yaml`.
2. Аудит покрытия требований подходом без переписывания плана.
3. Строгая ревизия плана по шести проверкам качества.
4. Отдельная фильтрация вопросов, уже отвеченных контекстом репозитория или
   относящихся к обратимым локальным деталям.
5. Одна попытка исправления, только если детерминированный валидатор отклонил
   результат ревизии.

Задач в плане нет. Каждый шаг подхода ссылается на ID требований, которые он
покрывает, а код агента проверяет, что непокрытых требований не осталось и что
каждое решение опирается на подтверждённые evidence. Принятый план сохраняется
в `.specs/<feature>/plan.yaml`.

## Граф задач

Отдельная фаза выводит исполняемый граф задач из принятого плана: черновик,
аудит, ревизия по десяти проверкам, фильтр вопросов, одно исправление. Решения
плана на этой фазе не пересматриваются.

Независимые задачи группируются в **волны зависимостей**. Волна вычисляется
кодом агента по графу, а не заявляется моделью: задачи одной волны не связаны
зависимостью и, поскольку политика запрещает неупорядоченную запись в один
файл, не конфликтуют по файлам. Задачи общей волны помечаются `[P]`, а модели
предписано не выдумывать зависимости, которые сериализуют независимую работу.

Каждая задача содержит ID требований и критериев приёмки, зависимости, файлы для
чтения, изменения или создания, команды проверки, условия завершения и риски.
Команды хранятся как отдельные program/args, а их файловые аргументы должны
существовать или создаваться раньше в графе задач.
Небольшие обратимые решения реализации перечисляются явно с файловыми evidence,
а не скрываются и не превращаются в лишние вопросы пользователю.
Код агента проверяет полное покрытие, известные ID, отсутствие циклов, безопасность
путей и принадлежность существующих файлов принятому discovery-контексту.

Недостающие продуктовые или архитектурные решения превращаются в вопросы.
Готовый граф задач исправляется до принятия пользователем и только затем
сохраняется как `.specs/<feature>/tasks.yaml`. Код реализации ни на одной из
этих фаз не пишется.

## Перекомпиляция фичи

Сохранённые артефакты — это входные данные, а не история. Правьте `spec.yaml` и
пересобирайте всё, что ниже, вместо ручной правки плана:

```bash
sddc --recompile plan -- registration     # пересобрать план, задачи, затем реализовать
sddc --recompile tasks -- registration    # оставить план, пересобрать задачи
sddc --recompile execute -- registration  # реализовать сохранённый граф задач
```

Имя фичи можно не указывать, если в `.specs` ровно одна фича.

## Интерфейс

В интерактивном терминале агент работает как приложение: сверху постоянная
«рельса» фаз с их состоянием, под ней живая область текущего этапа, снизу
статус-строка. Завершённые документы, ответы и события уходят в обычный
скроллбэк терминала, поэтому историю можно листать и копировать мышью, а после
выхода она остаётся на экране.

Весь вывод проходит через один драйвер (`src/ui/`), поэтому режимы
согласованы между собой:

- интерактивный TTY — приложение на Ink;
- `--plain` — стабильные строки;
- `--json` — по событию на строку;
- не-TTY или `--no-input` — построчный режим без запросов ввода.

Ни один этап пайплайна не пишет в stdout напрямую: это позволяет менять
интерфейс, не трогая workflow.

## Стоимость и кэширование префикса

Внутри одной фазы каждый этап добавляет вывод предыдущего к тому же объекту
контекста, поэтому всё до этой добавки повторяется дословно. Чтобы провайдер мог
этим воспользоваться, запрос собирается **контекстом вперёд, инструкцией назад**:
system-сообщение постоянно для всех этапов, а инструкция этапа идёт в конце
пользовательского сообщения. Если бы инструкция была в system, префикс расходился
бы с нулевого токена и кэширование не работало бы вовсе.

Это даёт экономию на провайдерах с автоматическим кэшированием префикса (OpenAI,
DeepSeek, большинство сборок vLLM). Провайдеры, требующие явных cache-точек,
через OpenAI-совместимый API их выразить не позволяют.

В конце запуска выводится сводка: число вызовов, входные и выходные токены и доля
входа, обслуженная из кэша. Доля показывается только если провайдер её сообщает —
по ней видно, действительно ли кэш работает.

## Параллельные волны

Задачи одной волны независимы по построению, а задержка модели доминирует в
запуске. Поэтому генерация предложений для соседей по волне идёт параллельно,
пока текущая задача ждёт проверки. Запись, верификация и подтверждение остаются
строго последовательными — терминал не должен вести два диалога сразу.

Упреждение применяется не ко всем задачам волны. Политика запрещает двум задачам
писать один файл без порядка, но **чтение чужой записи не запрещено**. Задача,
читающая файл, который пишет или создаёт её сосед по волне, готовится обычным
порядком: иначе её предложение строилось бы по содержимому, которое вот-вот
изменится.

В режиме `strict` упреждения нет вообще. Этот режим существует, чтобы
пользователь разрешал каждую задачу до начала работы над ней, и вызов модели до
подтверждения обессмысливал бы его.

## Язык

Язык интерфейса выбирается при запуске. Чтобы не отвечать на этот вопрос каждый
раз, задайте `SDDC_LANG=ru` или `SDDC_LANG=en` в `~/.config/sddc/.env` — тогда
вопрос не задаётся. Флаг `--lang` перекрывает и то, и другое.

Язык **артефактов** определяется отдельно и по-другому: не настройкой, а самим
содержимым документа. Модель пишет прозу на языке запроса, поэтому каждый
артефакт определяет свой язык по собственному тексту. Так русские требования не
окажутся под английскими заголовками, а один проект может содержать фичи на
разных языках без общей настройки.

Переводятся заголовки, подписи полей и значения статусов; идентификаторы, пути и
команды остаются как есть.

## Работа с артефактом на проверке

Когда артефакт ждёт решения, доступно пять действий:

- **Принять** — перейти к следующей фазе;
- **Показать документ полностью** — развернуть краткий итог;
- **Отредактировать самому** — открыть YAML в `$EDITOR`, поправить руками;
- **Попросить исправить** — описать словами, что не так, и пересобрать;
- **Принятые решения** — показать всё, что уже отвечено в этой фазе.

Прямое редактирование убирает модель из решения, для которого она не нужна:
описывать словами правку, которую проще внести самому, — потеря на двойном
переводе. Отредактированный YAML проверяется по схеме; если он невалиден, правка
отклоняется, а прежний артефакт остаётся на месте. Волны для графа задач
пересчитываются заново — их нельзя задать руками.

Редактирование и просмотр решений не тратят раунд правок: они ничего не меняют
выше по потоку.

Возврат к предыдущей фазе делается между запусками через `--recompile`.

## Формат артефактов

Каждый артефакт пишется в двух видах. YAML — машинный формат: его парсит и
проверяет пайплайн. Markdown рядом с ним (`spec.md`, `plan.md`, `tasks.md`,
`discovery.md`) существует для ревью: артефакт — это то, что человек утверждает,
а diff YAML для этого плохое место.

Markdown односторонний: его никто не читает обратно, поэтому он не может
разойтись с YAML в том, что именно было принято.

Отдельно пишется `quickstart.md` — сценарий приёмки: каждый критерий, задачи,
которые его покрывают, и команды, которые его доказывают. У него нет YAML-пары,
потому что его никто не парсит: он целиком выводится из `spec.yaml` и
`tasks.yaml`, а просить его у модели значило бы дать ей шанс разойтись с ними.

## Нестабильность и выборка

`temperature: 0` не делает обслуживаемую модель детерминированной: на один и тот же
вход граф задач получается разным от прогона к прогону. Бороться с этим
формулировками бесполезно — разброс идёт от инференса, а не от промпта.

Поэтому цель другая: не сделать граф стабильным, а сузить множество допустимых
графов так, чтобы **любой** прошедший образец был исполним. Тогда разброс из
проблемы превращается в ресурс — чем он шире, тем вероятнее, что какой-то образец
пройдёт.

Фаза графа задач берёт до `sampling.max_attempts` образцов (по умолчанию 3) и
принимает первый, прошедший валидаторы. Первый заход — полная цепочка
черновик/аудит/ревизия, последующие — починка с текстом отклонения, что дешевле и
осмысленнее, чем начинать заново.

Верификатор здесь бесплатный и детерминированный, поэтому лишний образец стоит
одного вызова модели и покупает реальный шанс на валидный артефакт. Это же
механизм rejection sampling, который понадобится для обучения маленькой модели.

## Владение критериями приёмки

Критерий приёмки принадлежит **ровно одной** задаче. Требование может обслуживаться
несколькими.

Основание простое: критерий приёмки — это тест, а у теста один дом. Если критерий
разделён между четырьмя задачами, то ни одна из них его не реализует, и проверка
«все заявленные критерии реализованы» становится невыполнимой. Разделение также
разрушает присвоение вины: провалившийся критерий больше не указывает на задачу.

Покрытие становится **разбиением**, а не просто покрытием, и именно поэтому его
можно проверить кодом.

Задача, которая обслуживает требование и не завершает ни одного критерия, оставляет
`acceptance` пустым — это законно. При включённом test-first критерием владеет та
задача, которая пишет проверяющий его тест, а реализация служит требованиям.

## Тест до реализации

Article III в SDD — «никакой реализации до теста» — помечен как непреложный. У нас
он выражен политикой, а не просьбой в промпте:

```yaml
changes:
  require_test_before_implementation: true
```

Когда правило включено, задача, меняющая **поведенческий** исходник, обязана
зависеть от отдельной более ранней задачи, которая пишет тест. Тест в той же
задаче не засчитывается: иначе слово «до» ничего не значило бы, а порядок — это
ровно то, о чём статья.

Изменения конфигурации, документации и файлов блокировок теста не требуют: в них
нет поведения, которое можно утверждать, и требование теста для них научило бы
только выключать правило.

Задача, которая пишет **только** тесты, обязана оставить проверку красной. Тест,
проходящий до того, как написана реализация, ничего не утверждает, поэтому зелёный
результат для такой задачи считается провалом. Ожидание выводится из списка файлов
задачи, а не заявляется моделью, — подделать его нельзя, как и волны.

Правило проверяется на графе, до запуска, и по умолчанию **выключено**. Включать
его по умолчанию до того, как корпус оценок покажет, что модель стабильно строит
подходящие графы, значило бы ронять каждый прогон.

## Оценка качества

Правка промпта или обрезка контекста меняет то, что выдаёт модель, и без замера
это ставка вслепую. Корпус оценок делает изменение измеримым.

Размечать ничего не нужно: сохранённая фича — это уже артефакты, которые
пользователь проверил и принял. Запись случая сводится к копированию.

```bash
sddc --eval-record -- registration   # записать принятый прогон как случай
sddc --eval                          # оценить корпус, без вызовов модели
sddc --eval --live                   # перегенерировать план и задачи, затем оценить
```

Оценка не изобретает свою шкалу, а переиспользует валидаторы пайплайна: они уже
задают, что здесь считается верным, их нельзя переубедить, и они работают без
модели. Проверяются `spec-valid`, `plan-valid`, `tasks-valid` и `tasks-policy`;
отдельно считаются разрывы покрытия — это не провал, но их число не должно расти.

Без `--live` корпус проигрывается офлайн: это ловит ситуацию, когда изменённый
валидатор начинает отвергать работу, которую пользователь уже принял. С `--live`
план и граф задач собираются заново из записанной спецификации — именно это
делает правку промпта или контекста проверяемой.

Команда возвращает ненулевой код выхода при провале, поэтому её можно повесить
на CI или pre-commit.

## Проверка согласованности

Сохранённые артефакты можно править вручную, поэтому агент записывает, из какой
версии входа получен каждый производный артефакт (`provenance.yaml`). Команда
проверяет расхождения, ничего не изменяя:

```bash
sddc --analyze -- registration
```

Она сообщает о двух видах проблем. **stale** — артефакт выведен из версии входа,
которой на диске уже нет: например, `spec.yaml` отредактировали, а `plan.yaml`
всё ещё отвечает на прежние требования. **gap** — требование или критерий
приёмки, который не покрыт ни одним шагом плана или задачей. Пофазные валидаторы
такие разрывы не видят, потому что каждый из них смотрит только на свою фазу.

## Диалог и лимиты

Ответы на уточняющие вопросы сохраняются в `.specs/session.yaml` сразу после
ввода. Если этап упадёт, повторный запуск того же запроса продолжит работу с уже
данными ответами, а не начнёт диалог заново. Сессия привязана к тексту запроса:
для другого запроса ответы не подставляются. После сохранения графа задач сессия
очищается, поскольку все ответы уже вошли в артефакты.

Число раундов ограничено политикой, чтобы модель не могла зациклить диалог:

```yaml
dialogue:
  max_clarification_rounds: 3
  max_revision_rounds: 5
```

## Политика и решения

План ограничивается детерминированной политикой, а не только мнением модели.
Встроенная политика разрешает одной задаче изменить не более шести файлов и
создать не более трёх, запрещает чувствительные пути, использует небольшой
список допустимых команд и отключает внешний доступ к сети. Изменение
зависимостей, конфигурации и миграций требует явного permission в задаче. Две
задачи могут изменять один файл только при однозначном порядке зависимостей.

Принципы, которые политика выразить не может — архитектурные правила, подход к
тестам, стиль — описываются в `.sddc/constitution.md`. Файл передаётся фазам
плана и задач как текст и никогда не парсится: политика запрещает, конституция
только информирует. Конфликт принципа со спекой должен быть зафиксирован как
раскрытое решение, а не разрешён молча.

Ограничения можно переопределить для проекта в `.sddc/policy.yaml`:

```yaml
version: 1
changes:
  max_files_per_task: 4
  max_generated_file_bytes: 131072
  require_dependency_permission: true
  require_test_before_implementation: false
execution:
  default_approval_mode: normal
  max_changed_lines_per_task: 400
  max_proposal_revisions: 1
  command_timeout_seconds: 120
  allow_git_checkpoints: false
commands:
  allowed_programs: [bun, node]
  allow_external_network: false
```

Переопределение валидируется и объединяется со значениями по умолчанию.
Некорректная политика останавливает запуск. После принятия плана пользователем
указанные в нём permissions считаются выданными только этому плану. Эффективная
политика сохраняется как `.specs/<feature>/policy.yaml`, поэтому результат можно
воспроизвести.

Также агент записывает `.specs/<feature>/decisions.yaml`. В нём хранятся
продуктовые требования, пользовательский контекст репозитория, обратимые решения
реализации и выданные разрешения с указанием владельца и источника. Поэтому
решение пользователя можно отличить от файлового evidence или вывода агента.
Исходные файлы и команды на этом этапе не выполняются.

## Контролируемое исполнение

После планирования показывается контракт с задачами, файлами, permissions,
командами и сетевой политикой. Реализация запускается только по отдельному
подтверждению. Задачи выполняются в порядке зависимостей. Модель получает
утверждённый scope и актуальные снимки, после чего возвращает полное содержимое
файлов либо явный blocker для перепланирования. Хост проверяет пути, операции,
лимиты строк и размера, трассировку требований и SHA-256 снимков.

Отдельный read-only вызов проверяет покрытие, scope, публичное поведение, секреты,
обработку ошибок, качество тестов и скрытые решения. Reviewer может отклонить
предложение, но не может его исправлять. Число повторов ограничено политикой.

- `strict` подтверждает scope задачи, файлы diff и каждую команду;
- `normal` подтверждает diff каждой задачи;
- `trusted` автоматически принимает обычные diff задач.

Чувствительные permissions и сетевые команды подтверждаются непосредственно
перед действием во всех режимах. Удаление файла из strict scope блокирует запуск
и требует пересмотра плана вместо частичной реализации.

Принятые изменения записываются атомарно, а verification-команды из плана
запускаются напрямую, без shell. Процесс наследует только небольшой список
переменных окружения. При ошибке команды все изменения текущей задачи
восстанавливаются, после чего пользователь решает, разрешить ли новую попытку.
Прогресс и ограниченный вывод команд сохраняются в
`.specs/<feature>/execution.yaml`.

После проверки можно продолжить, откатить задачу для новой версии или создать
явно разрешённый Git checkpoint. Resume возможен только при совпадении хэшей
завершённых файлов. Финальная приёмка показывает общий Git diff и результаты
проверок и позволяет вернуть незакоммиченную задачу текущей сессии на доработку.

Это защита на уровне приложения, а не изоляция операционной системы. Разрешённая
команда проекта всё ещё может выполнить произвольный код проекта, поэтому перед
подтверждением необходимо проверить и план, и diff.

## Статусы

- `ready` — данных достаточно, требования и критерии приёмки согласованы;
- `needs_clarification` — требуется решение пользователя;
- `needs_decomposition` — запрос содержит несколько независимо поставляемых
  возможностей.

## Запуск

```bash
curl -fsSL https://raw.githubusercontent.com/Aidamirrrrrr/sddc/master/install.sh | sh
sddc --init
sddc "Описание задачи"
```

Для предварительной проверки без изменения исходников используйте
`sddc --dry-run "Описание задачи"`. Режимы `--plain` и `--json` дают
стабильный вывод для терминала и автоматизации, `--no-input` запрещает prompts,
а `--debug` добавляет stack trace к ошибкам.

Для многострочного запроса:

```bash
sddc < task.txt
```

Принятая спека записывается в `.specs/<feature>/spec.yaml` текущего рабочего
проекта.

## Конфигурация

Команда `sddc --init` создаёт файл `~/.config/sddc/.env` с закрытыми
правами доступа. Перед первым обращением к модели заполните в нём значения:

```env
AI_API_TOKEN=your-token
AI_API_URL=https://chat.immers.cloud/v1/endpoints/model/generate/
AI_MODEL=model-id
AI_INPUT_USD_PER_MILLION=optional-input-price
AI_MAX_OUTPUT_TOKENS=optional-output-cap-or-off
AI_REQUEST_TIMEOUT_SECONDS=optional-seconds
SDDC_LANG=ru
SDDC_THEME=dark
```

`budget.max_model_calls` в `.sddc/policy.yaml` — потолок вызовов модели на весь прогон (по
умолчанию 400), а `--max-calls <n>` переопределяет его для одного запуска. Все остальные лимиты
ограничивают по одному циклу, а циклы вложены друг в друга — попытки задачи, витки лупа, тиражи
предложения, репары схемы, — поэтому они перемножаются, а не складываются. Это единственное место,
где видна вся эта арифметика. Небольшая фича измеряется примерно в тридцать вызовов от начала до
конца, так что потолок не должен срабатывать на нормальной работе.

`AI_MAX_OUTPUT_TOKENS` ограничивает **ответ** одного вызова модели (по умолчанию
32768, минимум 1024). Это не контекстное окно: окно ограничивает вход и здесь не
задаётся вовсе, а максимум вывода у модели на порядок меньше окна. У
reasoning-моделей размышления расходуют этот же бюджет, поэтому слишком маленькое
значение приводит к пустому ответу на тяжёлых этапах вроде `tasks-audit`. Если
пустой ответ всё же случился, агент делает повторную попытку с пониженным
reasoning, чтобы весь бюджет ушёл на сам ответ.

`AI_REQUEST_TIMEOUT_SECONDS` ограничивает, сколько один запрос может оставаться открытым (по
умолчанию 300, минимум 10). Соединение, которое открылось и замолчало, неотличимо от медленной
модели, поэтому без границы прогон без человека ждёт его вечно. Запрос по таймауту повторяется,
отменённый вами — нет.

`SDDC_LANG` и `SDDC_THEME` — это настройки, а не доступы, и обе записываются обратно при первом
ответе: выбор языка спрашивается один раз, а команды `/lang` и `/theme` внутри сессии сохраняют
новый выбор в тот же файл. `SDDC_THEME` принимает `dark`, `light` или `ansi`; если оставить пусто,
палитра определяется по терминалу — `NO_COLOR` или отсутствие `COLORTERM` включают `ansi`, а
`COLORFGBG` различает светлый и тёмный фон.

`AI_MAX_OUTPUT_TOKENS=off` вообще не отправляет ограничение — действует
собственный максимум модели. Это верная настройка для self-hosted эндпоинта или
тарифа без поштучной оплаты; при оплате за токены значение по умолчанию — это
осознанная граница у иначе ничем не ограниченного счёта.

Переменные окружения имеют приоритет над пользовательским конфигом. Для установки
версии из текущих исходников выполните `bun install && bun run install:local`.

Количество токенов приблизительное, поскольку токенизация зависит от модели.
Стоимость показывается только при заданном `AI_INPUT_USD_PER_MILLION`.

Для OpenAI-совместимого API Ollama используется тот же клиент:

```env
AI_API_TOKEN=ollama
AI_API_URL=http://127.0.0.1:11434/v1/
AI_MODEL=your-local-model
```

## Диагностика этапов

```bash
bun start --stage extract --thinking off -- "Описание задачи"
bun start --stage analyze --thinking on -- context.json
```

Доступные этапы: `extract`, `analyze`, `analysis-review`, `analysis-repair`,
`write`, `review`, `repository-select`, `repository-expand`,
`repository-discover`, `repository-review`, `repository-revise`,
`planning-draft`, `planning-audit`, `planning-review`, `planning-questions`,
`planning-repair`, `tasks-draft`, `tasks-audit`, `tasks-review`,
`tasks-questions`, `tasks-repair`, `execution-implement` и `execution-review`.

Кроме `extract`, этапы ожидают JSON-контекст предыдущих этапов. Это позволяет
проверять один вызов модели без повторного запуска всего pipeline. Thinking по
умолчанию выключен.

Подробнее о содержании исходного запроса: [Как составлять запросы](writing-requests.md).
