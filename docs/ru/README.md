# Документация Spec Agent

Spec Agent составляет спецификацию по исходному запросу и ответам пользователя.
Он работает как проверка качества требований: обнаруживает недостающие решения,
противоречия и слишком крупные задачи, но не придумывает ответы самостоятельно.

## Как работает pipeline

1. Из запроса извлекаются только явно указанные факты и язык запроса.
2. Единый анализ определяет готовность запроса, необходимость вопросов или
   декомпозиции.
3. Отдельный reviewer проверяет анализ по исходным фактам. Для вопросов и
   декомпозиции pipeline завершается после этого третьего вызова.
4. Для готового запроса формируется спецификация.
5. Спецификация проходит финальную проверку по чек-листу.

Таким образом, неполный или крупный запрос использует три обычных LLM-вызова,
а готовая спецификация — пять. Невалидный анализ получает один дополнительный
repair-вызов.

Если любой этап возвращает пустой или не соответствующий схеме structured
output, клиент отправляет модели исходный контекст и ошибку на одну повторную
попытку. Бесконечных retry нет.

В интерактивном терминале статус `needs_clarification` запускает новый раунд
вопросов. Ответы добавляются к исходному запросу, после чего весь pipeline
выполняется заново. Цикл заканчивается только со статусом `ready` или
`needs_decomposition`. Пустой ответ не принимается; прервать диалог можно через
`Ctrl+C`.

Готовая спецификация или декомпозиция полностью выводится в терминал и требует
явного решения: `accept` или `revise`. При отклонении пользователь описывает,
что именно нужно изменить. Отклонённая YAML-спека и комментарий добавляются в
контекст, после чего pipeline запускается заново. Только принятая версия
сохраняется как `spec.yaml`.

При чтении из pipe агент не может задавать вопросы или получить подтверждение,
поэтому выводит результат и сохраняет его как `spec.draft.yaml`.

## Исследование репозитория

После принятия спеки со статусом `ready` агент запускает read-only discovery:

1. Индексирует безопасные файлы проекта без чтения содержимого.
2. Модель рекомендует не более 24 релевантных файлов и объясняет каждый выбор.
3. Пользователь ищет, включает или отключает файлы и при необходимости добавляет
   контекст проекта.
4. Агент читает только подтверждённые текстовые файлы в пределах лимита размера.
5. Модель может запросить до восьми дополнительных файлов, после чего
   пользователь подтверждает расширенный набор.
6. Модель описывает стек, структуру, связанные файлы, соглашения, тесты,
   ограничения и неизвестные факты.
7. Второй вызов удаляет выводы без файловых evidence.
8. Discovery показывается пользователю и исправляется до явного принятия.

`.env`, приватные ключи, `.git`, `.specs`, зависимости и build output никогда не
передаются модели. Discovery ничего не проектирует и не изменяет. Результат
сохраняется как `.specs/<feature>/discovery.yaml`.

Селектор показывает причину рекомендации, поддерживает поиск по мере ввода и не
позволяет выбрать больше 24 файлов или 200 KiB. Дополнительный контекст считается
утверждением пользователя, но не файловым evidence.
Подтверждённые пути и пользовательский контекст записываются в `discovery.yaml`.
Рабочая область помечает рекомендованные, тестовые, конфигурационные и остальные
файлы, позволяет просматривать выбранные файлы, показывает оценку токенов и
стоимости и хранит переиспользуемые профили в `.specs/context-profiles/`.

Для принятой декомпозиции discovery не запускается: сначала должна быть выбрана
и описана конкретная подзадача.

## Планирование реализации

После принятия discovery планирование проходит несколько узких этапов:

1. Черновик графа небольших задач на основе `spec.yaml` и `discovery.yaml`.
2. Аудит покрытия требований и критериев приёмки без переписывания плана.
3. Строгая ревизия плана по десяти проверкам качества.
4. Отдельная фильтрация вопросов, уже отвеченных контекстом репозитория или
   относящихся к обратимым локальным деталям.
5. Одна попытка исправления, только если детерминированный валидатор отклонил
   результат ревизии.

Каждая задача содержит ID требований и критериев приёмки, зависимости, файлы для
чтения, изменения или создания, команды проверки, условия завершения и риски.
Команды хранятся как отдельные program/args, а их файловые аргументы должны
существовать или создаваться раньше в графе задач.
Небольшие обратимые решения реализации перечисляются явно с файловыми evidence,
а не скрываются и не превращаются в лишние вопросы пользователю.
Код агента проверяет полное покрытие, известные ID, отсутствие циклов, безопасность
путей и принадлежность существующих файлов принятому discovery-контексту.

Недостающие продуктовые или архитектурные решения превращаются в вопросы.
Готовый план исправляется до принятия пользователем и только затем сохраняется
как `.specs/<feature>/plan.yaml`. Код реализации на этом этапе не пишется.

## Статусы

- `ready` — данных достаточно, требования и критерии приёмки согласованы;
- `needs_clarification` — требуется решение пользователя;
- `needs_decomposition` — запрос содержит несколько независимо поставляемых
  возможностей.

## Запуск

```bash
bun install
bun start -- "Описание задачи"
```

Для многострочного запроса:

```bash
bun start < task.txt
```

Принятая спека записывается в `.specs/<feature>/spec.yaml` текущего рабочего
проекта.

## Конфигурация

```env
AI_API_TOKEN=your-token
AI_API_URL=https://chat.immers.cloud/v1/endpoints/model/generate/
AI_MODEL=model-id
AI_INPUT_USD_PER_MILLION=optional-input-price
```

Количество токенов приблизительное, поскольку токенизация зависит от модели.
Стоимость показывается только при заданном `AI_INPUT_USD_PER_MILLION`.

Для OpenAI-совместимого API Ollama используется тот же клиент:

```env
AI_API_TOKEN=ollama
AI_API_URL=http://127.0.0.1:11434/v1/
AI_MODEL=your-local-model
```

## Диагностика этапов

```bash
bun start --stage extract --thinking off -- "Описание задачи"
bun start --stage analyze --thinking on -- context.json
```

Доступные этапы: `extract`, `analyze`, `analysis-review`, `analysis-repair`,
`write`, `review`, `repository-select`, `repository-expand`,
`repository-discover`, `repository-review`, `repository-revise`,
`planning-draft`, `planning-audit`, `planning-review`, `planning-questions`,
`planning-repair`.

Кроме `extract`, этапы ожидают JSON-контекст предыдущих этапов. Это позволяет
проверять один вызов модели без повторного запуска всего pipeline. Thinking по
умолчанию выключен.

Подробнее о содержании исходного запроса: [Как составлять запросы](writing-requests.md).
